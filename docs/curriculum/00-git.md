# 0. Git

## 学習目標

Gitが「ファイルの同期ツール」ではなく、変更履歴を有向グラフとして管理する分散型バージョン管理システムであることを理解します。作業ツリー、ステージング領域、コミットの違いを説明し、安全にブランチを統合できることを目標にします。

## リポジトリと三つの領域

リポジトリは、現在のファイルだけでなく、各コミットの内容、親子関係、ブランチ名などを`.git`に保存します。

- 作業ツリー: 実際に編集しているファイル
- ステージング領域: 次のコミットへ含める変更
- リポジトリ: 確定済みのコミット履歴

```bash
git init
git status
git add README.md
git diff --staged
git commit -m "Document project requirements"
```

`git add`はファイル名を予約する操作ではなく、その時点の内容をステージします。追加後に再編集した部分は、もう一度`git add`するまで同じコミットには入りません。`git status`と`git diff`をコミット前に確認する習慣が、意図しない変更の混入を防ぎます。

## 良いコミット

コミットは、レビューや不具合調査で扱える最小の論理単位にします。「認証を実装してCSSも整理」のように目的の異なる変更を混ぜないでください。メッセージは変更内容だけでなく、目的が分かるように書きます。秘密鍵、`.env`、本番データ、個人情報は履歴へ入れてはいけません。一度公開した秘密は削除コミットだけでは履歴に残るため、認証情報の失効・再発行が必要です。

```gitignore
/.env
/log/*
/tmp/*
!/log/.keep
!/tmp/.keep
```

## ブランチと統合

ブランチはコミットを指す可動ラベルです。機能ごとに分けると、未完成の変更を既定ブランチから隔離できます。

```bash
git switch -c feature/post-likes
git add app/models/like.rb
git commit -m "Prevent duplicate likes per user"
git switch main
git merge feature/post-likes
```

マージ競合は「Gitの故障」ではなく、同じ箇所に異なる変更があり、自動で正解を決められない状態です。競合マーカーを機械的に消すのではなく、両方の変更目的を確認し、完成形へ編集してテストします。

## リモートとの共同作業

`fetch`はリモートの履歴を取得するだけで作業ブランチを変更しません。`pull`は通常、取得と統合を連続して行います。何が統合されるか理解したい場合は、`git fetch`後にログや差分を確認します。履歴を書き換えるrebaseやforce pushは、共有済みブランチでは他者の作業を失わせる危険があります。

## Instagramクローンへの応用

`feature/authentication`、`feature/post-images`、`feature/follows`のように機能を分けます。データベース変更を含むブランチでは、マイグレーションとモデル、テストを同じ論理変更としてレビュー可能にします。Pull Requestには目的、主要な設計判断、確認手順、画面変更を記載します。

## よくある誤り

- `git add .`と`git commit`を差分確認なしで実行する
- エディタ設定、生成ログ、認証情報まで追加する
- 大量の無関係な変更を一つのコミットへまとめる
- 競合解消後にテストせず統合する
- 公開ブランチを不用意にrebaseしてforce pushする

## 演習

1. 新しいリポジトリを作り、README追加と`.gitignore`追加を別々にコミットしてください。
2. 二つのブランチでREADMEの同じ行を変更し、競合を発生させて意図した文章へ統合してください。
3. `git log --oneline --graph --all`を実行し、ブランチとコミットの関係を説明してください。

## 確認チェックリスト

- 作業ツリー、ステージ、コミットの差を説明できる
- コミット前にステージ済み差分を確認できる
- 競合の原因を理解して解消できる
- 秘密情報を履歴へ入れない理由を説明できる
- `fetch`、`pull`、`merge`の役割を区別できる

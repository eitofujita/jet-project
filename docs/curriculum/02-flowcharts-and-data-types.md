# 2. フローチャートとデータ型

## 学習目標

要件を入力・処理・出力へ分解し、分岐や反復を実装前に整理できるようにします。また、Rubyの主要なデータ型を、保存したい情報と操作の性質に応じて選択できることを目指します。

## 処理を設計する

フローチャートは、開始・終了、処理、判断、入出力を図形と矢印で表します。図を描く目的は装飾ではなく、条件漏れ、終了しない反復、例外経路を実装前に発見することです。

例として「投稿へいいねする」を分解します。

1. ログイン中のユーザーと対象投稿を入力として受け取る。
2. 投稿が存在するか判断し、存在しなければ404を返す。
3. 同じユーザーのLikeが存在するか調べる。
4. 存在すれば削除し、なければ作成する。
5. 更新後の件数を返す。

ただし、同時リクエストでは「確認後に作成」だけでは重複し得ます。最終的な一意性はデータベース制約でも保証する必要があります。図は正常系だけでなく、未認証、不正入力、権限不足、保存失敗も含めます。

## 基本データ型

```ruby
published = true                 # TrueClass / FalseClass
caption = "夕焼け"               # String
like_count = 12                  # Integer
score = 4.5                      # Float
tags = ["sky", "travel"]         # Array
post = { id: 1, caption: caption } # Hash
missing = nil                    # NilClass
```

- `Integer`: 件数やID。金額にFloatを使うと丸め誤差が出るため、整数の最小単位やDecimalを使います。
- `String`: 文字列。破壊的メソッドは元のオブジェクトを変えることがあります。
- `Array`: 順序付きの複数要素。添字は0から始まります。
- `Hash`: キーと値の対応。属性名にはSymbol、外部JSONのキーにはStringが現れることがあります。
- `nil`: 値が存在しないことを表します。空文字列や0とは意味が異なります。

## Symbol、同一性、変更可能性

```ruby
params = { username: "mina", admin: false }
params[:username]

first = "hello"
second = first
second.upcase!
puts first # HELLO
```

変数`first`と`second`が同じ変更可能なStringを参照するため、破壊的変更が両方から見えます。予期しない共有を避けるには、新しい値を返す非破壊メソッドや`dup`、不変な値を検討します。

## 型変換と入力検証

`"12".to_i`は12になりますが、`"abc".to_i`も0になり、入力誤りを隠します。厳密に検証する場合は`Integer("abc")`の例外を処理するか、`Integer(value, exception: false)`で`nil`を検出します。型変換できることと、業務上有効な値であることは別です。投稿本文の長さ、許可する状態、数値範囲も検証します。

## Instagramクローンへの応用

画面入力はHashに近いParametersとして届き、投稿一覧はRelationまたは配列として扱われます。状態をStringで自由入力にすると誤記が混ざるため、enumや許可値で制約します。`nil`を許す列は「未設定」が業務上意味を持つか確認します。

## よくある誤り

- `0`を偽だと考える
- ArrayとHashの用途を区別しない
- StringキーとSymbolキーを混同する
- `to_i`で不正入力が0になることを見落とす
- アプリ側の事前確認だけで一意性を保証する

## 演習

1. ユーザー登録処理の正常系と、重複メール・空パスワードの経路をフローチャート化してください。
2. 投稿をHashで表し、タグ追加、公開済み判定、いいね数表示を実装してください。
3. 文字列入力を1以上100以下の整数として安全に検証してください。

- 主要型と適した用途を説明できる
- `nil`と空値の違いを説明できる
- 破壊的操作による参照共有の影響を理解している
